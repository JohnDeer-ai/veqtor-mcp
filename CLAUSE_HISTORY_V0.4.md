# Stage 3C evidence-bound paragraph history v0.4 specification

## Status and non-implementation boundary

This document freezes the preimplementation contract for the first Stage 3C
product slice. The filename uses the broader product phrase "clause history",
but the first slice traces exactly one paragraph. It does not identify or join
a semantic or multi-paragraph clause.

The future MCP tool name is `trace_paragraph_history`; its permanent
success-record pair will be
`(trace_paragraph_history, paragraph_history.v1)`. The implementation will
advertise MCP contract `veqtor.mcp.v0.4` only after that new surface and the
companion quote-verification contract described below are complete.

This specification changes no runtime behavior. Source version `0.3.0` remains
an eight-tool `veqtor.mcp.v0.3` implementation. Writing this document does not
register a ninth tool, change `verify_quote`, create a journal record type,
accept an installed artifact, or publish a release. Code, package, CI,
installed-wheel, Claude Desktop and publication acceptance remain separate
gates.

"Read-only" here means that the tool never changes a candidate DOCX and never
produces a new DOCX. A successful MCP call may append one private local
decision record, so the complete call is stateful and is not side-effect-free.
Its annotations therefore reuse the local-journaling tuple exactly:
`readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: false` and
`openWorldHint: false`.

## Product job in plain language

The user starts from one exact paragraph in the document they have chosen as
the last position of a declared file sequence. Veqtor then walks backward one
position at a time and answers a narrow question:

> What exact paragraph wording can these DOCX snapshots mechanically connect
> to the selected wording, and where does the available evidence stop?

For each file observation, Veqtor may report:

- the same complete accepted/current wording appears exactly once;
- the next-position file still contains pending revisions whose mechanically
  rejected text projection is exactly equal to one accepted/current paragraph
  in this position;
- more than one exact candidate exists; or
- no unique answer is available because the relationship is absent,
  incomplete or blocked by an earlier ambiguity.

The planned slice addresses the main product gap left by Stage 3B. Round Map
can prove exact accepted/current equality, but a heavily negotiated paragraph
normally changes in every file and therefore remains unresolved. Stage 3C can
additionally use the change markup preserved inside a higher-position file to
expose a second, strictly defined text projection and compare it exactly with
another immutable snapshot.

The result is structured JSON for a host model to format as a history brief.
It is not a narrative generated by Veqtor, a document-wide reconstruction, or
a sendable redline.

## Three evidence layers

The product keeps three conceptually different layers separate:

1. **Machine fact.** Veqtor derives a bounded observation from exact captured
   DOCX bytes and can reproduce the comparison.
2. **Caller assertion.** A future caller may identify a relationship that the
   machine cannot prove. Such an assertion would need hash-bound references,
   a closed vocabulary, conflict preservation, explicit retention rules and
   `attribution_verified: false`.
3. **Host/model interpretation.** A host may explain why a change matters or
   ask a lawyer to resolve an open question. That interpretation is outside
   the Veqtor result.

Only the first layer is accepted by this first slice. There is no
`caller_assertions` input. This avoids turning a model-supplied statement into
a lawyer statement and avoids storing free text verbatim in the current raw
journal. A later assertion contract must not upgrade machine resolution or use
last-write-wins conflict handling.

Reproduction requires the same exact source bytes to remain available. The
local record binds hashes, policies and outcomes; it neither archives the DOCX
snapshots nor reconstructs their contents from digests. Stage 3C is therefore
not an evidence repository or a chain-of-custody system.

## Closed reading projections

### Accepted/current reading

`accepted_current_v1` is reused unchanged from Stage 3A. Its exact Unicode text
and `paragraph_text_sha256` remain the identity carried by
`paragraph_ref.v1`.

### Rejected-pending text projection

The new derived reading is named
`pending_text_revisions_rejected_v1`. It means:

> the literal paragraph text obtained by rejecting every supported, still-
> pending inline text revision represented in this one DOCX snapshot.

It is deliberately not named `original`, `prior reading` or `previous round`.
It does not say that the projection was ever sent as a separate document, that
the adjacent lower position is chronological, or that all underlying revision
layers remain encoded in the file.

Rejecting all supported pending inline revisions is not necessarily a one-step
undo. With stacked or nested pending revisions, the projection may expose
wording older than the immediately adjacent declared file. Only exact equality
with that adjacent captured observation creates a relationship.

The implementation must define a new ancestor-aware projection. The existing
`text_atom(..., include_deleted_text=True)` primitive is not this projection
and cannot be used as one without the validation and visibility rules below.

### Literal visibility table

For supported text atoms (`w:t`, context-valid `w:delText`, `w:tab`, `w:br`,
`w:cr` and `w:noBreakHyphen`), visibility is closed as follows:

| Atom context within the paragraph | `accepted_current_v1` | `pending_text_revisions_rejected_v1` |
| --- | --- | --- |
| no text-revision ancestor | visible | visible |
| any `w:ins` ancestor | visible unless hidden by a deletion-like ancestor under the existing current policy | hidden |
| any `w:moveTo` ancestor | visible unless hidden by a deletion-like ancestor under the existing current policy | hidden |
| `w:del` ancestor and no `w:ins`/`w:moveTo` ancestor | hidden | visible |
| `w:moveFrom` ancestor and no `w:ins`/`w:moveTo` ancestor | hidden | visible |

For the rejected projection, an insertion-like ancestor (`w:ins` or
`w:moveTo`) always wins and hides the atom. Otherwise a deletion-like ancestor
(`w:del` or `w:moveFrom`) reveals its supported atom. A plain supported atom
remains visible. This priority is normative for mixed and nested wrappers.

The v0.4 projection adds a maximum combined text/move-revision wrapper depth of
two. The existing extraction guard covers nested `w:ins`/`w:del`; it is not by
itself sufficient for this broader rule. One over the new combined limit
refuses the complete tool call with `resource_limit_exceeded` and metadata
`limit: revision_nesting_depth`, `allowed_count: 2` and the observed count; it
never returns a shallower approximation.

`w:moveFrom` and `w:moveTo` participate only in literal wrapper visibility.
The tool does not pair move ranges and never emits an event or conclusion that
text "was moved".

### Projection availability

Every rejected-pending projection exposes two independent axes:

- `projection_status: complete | unavailable`; and
- when complete, `text_state: empty | nonempty` plus a separate
  `equals_current: boolean`.

This avoids treating `equals_current` as an alternative to empty/non-empty.
The exact object is:

```json
{
  "schema_version": "paragraph_projection.v1",
  "mode": "pending_text_revisions_rejected_v1",
  "projection_status": "complete",
  "unavailable_reasons": [],
  "text_state": "nonempty",
  "equals_current": false,
  "has_non_whitespace": true,
  "match_eligible": true,
  "projection_text_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "text_length": 137,
  "text": "Except as set out in Clause 14.3 ...",
  "move_wrapper_visibility_applied": true,
  "move_pairing": "not_attempted"
}
```

All keys are required. For `projection_status: unavailable`,
`unavailable_reasons` contains one or more of the closed reasons below;
`text_state`,
`equals_current`, `projection_text_sha256`, `text_length` and `text` are null;
`has_non_whitespace` and `match_eligible` are false. For a complete projection,
`unavailable_reasons` is empty, `text` is the complete bounded string and the
hash covers its exact Unicode scalar sequence.

For a complete projection, `match_eligible` is true if and only if
`text_state: nonempty`, `has_non_whitespace: true` and
`equals_current: false`; it is false in every other case. An implementation
cannot suppress an otherwise eligible rejected projection by setting this flag
to false.

`move_wrapper_visibility_applied` is true exactly when a supported
`w:moveFrom` or `w:moveTo` wrapper occurs in the selected paragraph and the
closed visibility rule is evaluated, and false otherwise; it is false when the
projection is unavailable. `move_pairing` is always
`not_attempted` in this schema.

The closed unavailability reasons, and their canonical array order, are:

- `stray_deleted_text` — `w:delText` is outside a valid `w:del` or
  `w:moveFrom` context;
- `existence_affecting_revision` — one or more members of the closed
  paragraph/row/cell/table/section set below affects the paragraph; or
- `declared_scope_incomplete` — an excluded or unknown text-bearing subtree
  prevents a complete projection under `canonical_body_flow_v1`.

The array contains unique values in that order, so simultaneous failures are
preserved rather than reduced by an arbitrary precedence rule.

An illegally placed text/move wrapper that cannot receive the closed ancestor
rule is not a fourth per-paragraph state: the candidate refuses with
`file_unextractable`. This keeps malformed package structure distinct from a
well-formed paragraph whose rejected projection is explicitly unavailable.

Availability is determined by a separate paragraph-structural-context scan,
not only by walking text-atom ancestors. The exact existence-affecting set is
`paragraphMarkIns`, `paragraphMarkDel`, `trPrIns`, `trPrDel`, `tcPrIns`,
`tcPrDel`, `tblPrIns`, `tblPrDel`, `sectPrIns`, `sectPrDel`, `cellIns` and
`cellDel` under the existing `revision_inventory.v2` classifier. A paragraph-
mark occurrence affects its owning paragraph. A row, cell or table occurrence
affects every canonical paragraph under that owning structural element. A
section-property occurrence affects the canonical paragraph whose `w:pPr`
owns it; a body-level occurrence outside a paragraph is text-neutral for this
projection. Stray text or an excluded/unknown text-bearing subtree affects only
the paragraph containing it. If an occurrence cannot be attributed under
these rules, the candidate DOCX refuses with `file_unextractable` rather than
poisoning an unspecified scope.

Text-neutral property history such as `w:rPrChange`, an ordinary
`w:pPrChange`, or numbering/formatting metadata does not by itself make the
literal text projection unavailable. It is counted as unsupported metadata and
does not become text or a legal-formatting conclusion. Paragraph-mark
insertions/deletions and row/cell existence changes are different: they make
the affected paragraph projection unavailable.

A complete empty projection proves only that this supported rejected text
projection is empty. It does not prove that the paragraph did not exist, that
the clause is new, or that a party inserted it. A whitespace-only projection is
`nonempty` but has `has_non_whitespace: false`. Neither empty nor whitespace-
only text is match-eligible.

If rejected and accepted/current strings are exactly equal,
`equals_current: true` and `match_eligible: false`. The unchanged relationship
is represented, if applicable, by accepted/current equality rather than by a
redundant rejected-projection edge.

## Closed machine-evidence vocabulary

There are two paragraph relationship classes. Neither is a semantic or
chronological relationship.

### `exact_content_equality`

This reuses the Stage 3B claim: two complete, non-whitespace
`accepted_current_v1` paragraph strings in different document observations
are exactly equal. Equal SHA-256 values are a candidate shortcut only; the
complete Unicode strings must also be compared.

Stage 3C wraps that basis in observation-scoped endpoints. Distinct
`observation_id` values are required, but equal content-level `paragraph_id`
values are allowed for byte-identical files at different paths; this is not a
self-relationship because the file observations are distinct.

### `rejected_projection_equality`

For adjacent declared positions `N-1` and `N`, this states only that the
complete `pending_text_revisions_rejected_v1` projection of the selected
paragraph at position `N` is exactly equal to the complete
`accepted_current_v1` text of one paragraph at position `N-1`.

The relationship is eligible only when:

- both observations come from immutable bytes captured by the same call;
- the rejected projection is `complete`, non-empty, has non-whitespace text,
  differs from its own accepted/current text and is `match_eligible`;
- the two text SHA-256 values agree; and
- the complete Unicode strings are then compared and agree exactly.

The relationship basis contains exactly:

```json
{
  "schema_version": "rejected_projection_equality_basis.v1",
  "evidence_class": "projection_text_equality_only",
  "part_name": "word/document.xml",
  "container_policy": "canonical_body_flow_v1",
  "lower_observation_id": "rm_obs_v1:...",
  "higher_observation_id": "rm_obs_v1:...",
  "lower_paragraph_observation_id": "ph_par_obs_v1:...",
  "higher_paragraph_observation_id": "ph_par_obs_v1:...",
  "higher_position_projection": "pending_text_revisions_rejected_v1",
  "lower_position_projection": "accepted_current_v1",
  "lower_current_text_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "higher_rejected_projection_text_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "higher_current_text_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "comparison": "sha256_then_full_unicode_equality_v1",
  "full_text_compared": true,
  "semantic_identity": "not_claimed",
  "direction_semantics": "projection_role_only",
  "derivation_recorded": false,
  "lineage_verified": false,
  "chronology_verified": false,
  "authorship_verified": false,
  "time_verified": false
}
```

The two compared hashes equal each other and the relationship's
`comparison_text_sha256`; `higher_current_text_sha256` differs from them. The
observation and paragraph-observation identities equal the outer relationship
endpoints. These invariants are part of relationship validation and identity.

The direction identifies projection roles and declared positions only. It does
not say that position `N` was created after position `N-1`.

No relationship is created from filename order, mtime, OOXML author/date,
labels, headings, similarity, an empty/whitespace projection, an unavailable
projection, or a projection equal to its own current text.

## Backward trace algorithm

The first slice deliberately implements one bounded direction instead of a
general history graph.

1. The seed must resolve in the last position of the declared complete file
   sequence. Otherwise the input fails with
   `seed_not_last_declared_position`.
2. The seed entry has `entry_role: seed` and no `resolution` object. It is not
   labelled `exact_unique`, because the caller supplied its exact identity.
3. Starting from the selected seed paragraph, the tool visits the immediately
   preceding declared position.
4. It compares the selected higher-position paragraph's complete
   accepted/current text with every complete, non-whitespace accepted/current
   paragraph in the lower-position document.
5. If the higher-position rejected projection is complete and match-eligible,
   it is also compared with every such lower-position paragraph.
6. Candidate paragraph identities from both comparison classes are unioned.
   Because an eligible rejected projection must differ from the selected
   paragraph's current text, one lower paragraph cannot satisfy both classes.
7. Exactly one candidate produces `exact_unique`, selects that paragraph and
   permits the next backward step. More than one candidate produces
   `ambiguous`. Zero candidates produces `unresolved`.
8. If the rejected projection is unavailable, a lone current-equality
   candidate is reported as a positive fact but cannot be declared unique:
   resolution is `unresolved/rejected_projection_unavailable` because another
   rejected-projection candidate cannot be excluded.
9. After `ambiguous` or `unresolved`, automatic propagation stops. Every
   still-lower observation remains explicit and unresolved; the tool does not
   jump over the gap or restart from a heading/navigation guess.

The rejected-projection status of a newly selected lower paragraph affects
only the next step toward a still-lower position. It does not retroactively
weaken the exact relationship that selected that paragraph from its higher
neighbor. At position zero it is still reported for completeness, but there is
no further propagation decision.

The first slice does not walk forward, compare every file directly with the
seed, or compare non-adjacent declared positions. A later expansion requires a
new acceptance contract.

## Resolution and navigation

Every non-seed observation has exactly one closed resolution:

- `exact_unique` — exactly one candidate paragraph identity exists across the
  union of eligible mechanical evidence classes and no incomplete projection
  can hide an additional candidate;
- `ambiguous` — two or more positive exact candidate identities exist; or
- `unresolved` — no unique mechanical selection is available.

The closed reason vocabulary is:

| State | Allowed reasons |
| --- | --- |
| `exact_unique` | `exact_current_unique`, `rejected_projection_unique` |
| `ambiguous` | `multiple_exact_candidates` |
| `unresolved` | `rejected_projection_unavailable`, `navigation_only`, `no_match_in_declared_scope`, `blocked_by_higher_ambiguity`, `blocked_by_higher_unresolved` |

State and reason use this first-match precedence:

| Condition | State/reason | Lower propagation |
| --- | --- | --- |
| higher step is `ambiguous` | `unresolved/blocked_by_higher_ambiguity` | stop; do not compare |
| higher step is `unresolved` | `unresolved/blocked_by_higher_unresolved` | stop; do not compare |
| two or more distinct positive candidate refs are already known | `ambiguous/multiple_exact_candidates` | stop |
| rejected projection unavailable and zero or one current candidate is known | `unresolved/rejected_projection_unavailable` | stop |
| complete projection and exactly one current candidate, no rejected candidate | `exact_unique/exact_current_unique` | continue from it |
| complete projection and exactly one rejected candidate, no current candidate | `exact_unique/rejected_projection_unique` | continue from it |
| complete projection, no candidates, one or more navigation candidates | `unresolved/navigation_only` | stop |
| complete projection, no text or navigation candidate | `unresolved/no_match_in_declared_scope` | stop |

Because eligible current and rejected strings differ, their candidate sets are
disjoint. In particular, one unique current candidate plus a different unique
rejected candidate is `ambiguous`, not a preferred-current selection. If two
or more current candidates are already positive, projection unavailability
cannot weaken that known ambiguity.

`exact_unique` means a unique mechanically connected paragraph in that file
observation. It does not mean a semantically verified same clause.

As a navigation aid, every non-seed observation, including one blocked by a
higher ambiguity or unresolved step, reports exact seed-section label/heading
candidates under the existing Stage 3B navigation policy. The seed reports the
canonical empty navigation summary. Navigation candidates never enter the
candidate union, never permit propagation and never change `unresolved` to
either exact state. Duplicate headings remain separate candidates; no best
candidate is selected.

`unresolved` never means deleted, inserted, new, rejected, restored, conceded
or absent from the whole DOCX.

## Future MCP input

The future named arguments are:

```json
{
  "folder": "/Users/example/Deals/Acme",
  "seed": {
    "schema_version": "paragraph_history_seed.v1",
    "path": "/Users/example/Deals/Acme/04-current.docx",
    "paragraph_ref": {
      "schema_version": "paragraph_ref.v1",
      "ref_type": "paragraph",
      "file_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "part_name": "word/document.xml",
      "paragraph_index": 61,
      "paragraph_text_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
      "reading_mode": "accepted_current_v1",
      "container_policy": "canonical_body_flow_v1"
    }
  },
  "order_basis": {
    "schema_version": "paragraph_history_order.v1",
    "kind": "filename_lexicographic_v1"
  },
  "cursor": null,
  "max_items": 50
}
```

The named input surface contains only `folder`, `seed`, `order_basis`,
`cursor` and `max_items`; `cursor` and `max_items` may be omitted for the first
page/default size. All nested objects are closed. Because the current MCPServer
transport may discard unknown top-level named arguments before the tool runs,
callers must use only this advertised surface and cannot treat an ignored extra
field as accepted policy.

`order_basis` is required; there is no implicit default. Its tagged union is:

```json
{
  "schema_version": "paragraph_history_order.v1",
  "kind": "filename_lexicographic_v1"
}
```

or:

```json
{
  "schema_version": "paragraph_history_order.v1",
  "kind": "explicit_filename_sequence_v1",
  "ordered_filenames": [
    "01-initial.docx",
    "02-counterparty.docx",
    "03-our-counter.docx",
    "04-current.docx"
  ]
}
```

The lexicographic rule is the existing case-folded filename order with exact
spelling as the tie-breaker. The explicit sequence must name every direct
candidate DOCX exactly once, with no extra or duplicate name. Both modes are
position-only and return `chronology_verified: false`. Positions are zero-based
indexes into that exact declared order.

The first slice always scans the complete direct-folder candidate set. It does
not accept a subset manifest. Supporting subsets later would require separate
candidate-versus-declared coverage counts and would bind every negative claim
to that subset.

`seed` contains exactly the fields shown. Its path must be one safe direct
candidate in `folder`; its complete `paragraph_ref.v1` must re-resolve against
the captured bytes. A legacy change-unit anchor, `section_ref.v1`, or a second
"prior" anchor type is invalid. The current paragraph must contain at least one
non-whitespace Unicode scalar.

The first slice has no text-suppression switch: a live result always contains
bounded verbatim strings for selected paragraphs and their change units.
`max_items` defaults to 50 and is an integer from 1 through 100; booleans are
not integers. `cursor` is null/absent on the first page and a valid `ph1`
cursor thereafter.

There is no input for chronology, confidence, fuzzy search, semantic matching,
baseline selection, accept/reject disposition, normalization, output DOCX, or
caller assertions.

## Candidate capture and immutable authority

Candidate enumeration, path safety and byte capture reuse the implemented
Stage 3B Round Map filesystem rules:

- only direct, case-insensitive `.docx` candidates are considered;
- lock files beginning `~$` and non-DOCX names are ignored; every remaining
  `.docx`-named entry, including a directory with that suffix, is a candidate
  and must pass the one-link regular-file check;
- symlink, non-regular, multi-link, identity-swapped or drifting candidates
  refuse the complete operation;
- every candidate is opened relative to the validated folder descriptor with
  no-follow semantics; and
- pre/post-read descriptor identity plus immediate post-read name identity must
  agree before the captured bytes become the authority for the call.

For each candidate, accepted/current text, rejected-pending text, coverage,
hashes and paragraph change units must derive from that same captured byte
string. A path-based second read is forbidden. Existing byte-level helpers may
be reused internally; no new public byte API is required.

The complete call returns one entry per filename observation. Byte-identical
files under two different safe names remain two observations and two declared
positions even though their document and paragraph content identities agree.

The snapshot expressly reports `filesystem_cross_file_atomic: false`. Veqtor
captures and validates each file safely, but the operating system does not
provide one atomic transaction across an ordinary folder of separate files.

The top-level successful object has these required fields:

| Field | Exact value/type |
| --- | --- |
| `schema_version` | `paragraph_history.v1` |
| `status` | `ok` |
| `seed` | closed path-free seed identity plus declared seed position |
| `ordering_source` | `filename_lexicographic_v1 \| explicit_filename_sequence_v1` |
| `order_basis` | closed position-only object with `chronology_verified: false` |
| `result_order` | `seed_then_descending_position_v1` |
| `snapshot` | closed `paragraph_history_snapshot.v1` object |
| `observations` | ordered page of closed observation entries |
| `coverage` | closed coverage/count object |
| `limits` | closed fixed-limits object |
| `next_cursor` | valid `ph1` cursor or null |
| `producer` | common producer object for contract v0.4 |
| `record_id` | `dr_[0-9]+` or null |
| `record_status` | `written \| disabled \| write_failed` |

`record_error` is allowed only with `record_status: write_failed`. All other
top-level fields are required and non-null except `next_cursor` and
`record_id`.

Every nested object defined by this specification is closed. Unknown nested
fields are invalid. Text SHA-256 values hash the exact UTF-8 bytes of the
complete Unicode string with no JSON wrapper or normalization. Object/list
digests use the existing `canonical_json_v1` encoding.

For readability, `{}` and `[]` inside the structural examples below mark a
separately defined complete nested object or array. They are not permission to
substitute a literal empty object/array where the referenced schema requires
fields or items.

### Stable identities

The result reuses the implemented Stage 3B identities rather than creating
aliases:

- `document_id` is `rm_doc_v1:<file_sha256>`;
- `paragraph_id` is `rm_par_v1:<canonical_json_v1 SHA-256 of the complete
  paragraph_ref.v1>`; and
- `observation_id` is `rm_obs_v1:<canonical_json_v1 SHA-256 of the existing
  document_observation_identity.v1 payload containing document_id and the
  canonical live path>`.

Stage 3C additionally uses `paragraph_observation_id` as
`ph_par_obs_v1:<canonical_json_v1 SHA-256>` over exactly
this object with the complete ref:

```json
{
  "schema_version": "paragraph_observation_identity.v1",
  "observation_id": "rm_obs_v1:...",
  "paragraph_ref": {}
}
```

This is the endpoint/candidate identity used by the trace.
It prevents byte-identical files at different paths from collapsing into a
self-edge merely because their content-level `paragraph_id` is equal.

A history relationship id is
`ph_rel_v1:<canonical_json_v1 SHA-256>` over exactly
this object:

```json
{
  "schema_version": "paragraph_history_relationship_identity.v1",
  "relationship_type": "rejected_projection_equality",
  "lower_position": 2,
  "higher_position": 3,
  "lower_paragraph_observation_id": "ph_par_obs_v1:...",
  "higher_paragraph_observation_id": "ph_par_obs_v1:...",
  "comparison_text_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "basis": {}
}
```

Relationship support
does not enter paragraph identity. A rename therefore changes the observation
identity but not byte or paragraph content identity.

### Closed order and snapshot objects

The returned `order_basis` contains exactly:

```json
{
  "schema_version": "paragraph_history_order_result.v1",
  "kind": "filename_lexicographic_v1",
  "rule": "casefold_then_exact",
  "position_semantics": "declared_position_only",
  "chronology_verified": false,
  "filename_manifest_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

For explicit order, `kind` is `explicit_filename_sequence_v1` and `rule` is
`exact_sequence`; every other key is unchanged. The manifest digest covers the
complete exact ordered filename array, not a sorted set.

More precisely, `filename_manifest_sha256` is the `canonical_json_v1` SHA-256
of exactly this object, with `ordering_source` equal to the returned top-level
value and `filenames` equal to the complete ascending-position sequence:

```json
{
  "schema_version": "round_map_filename_manifest.v1",
  "ordering_source": "filename_lexicographic_v1",
  "filenames": ["01-draft.docx", "02-counter.docx"]
}
```

For explicit order the value is `explicit_filename_sequence_v1`; omission of
an explicit sequence is normalized to the computed lexicographic sequence
before hashing.

The returned `snapshot` contains exactly:

```json
{
  "schema_version": "paragraph_history_snapshot.v1",
  "filesystem_snapshot_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
```

## Snapshot and cursor binding

The already-defined `paragraph_history_snapshot.v1` digests bind exactly:

- the safe candidate filename manifest and each filename observation's exact
  file SHA-256;
- the complete order declaration and seed position;
- the exact seed `paragraph_ref.v1`;
- `accepted_current_v1`, `pending_text_revisions_rejected_v1`,
  `canonical_body_flow_v1` and all projection/normalization policy versions;
- fixed resource limits;
- `result_order: seed_then_descending_position_v1`;
- the complete ordered result-set digest; and
- the fixed cursor policy version through `projection_policy_sha256`.

Every later page recaptures and recomputes the same authority. Candidate-set or
byte drift yields `cursor_mismatch`; drift of the seed bytes/reference retains
the more specific seed/hash error. Page-size changes within the fixed maximum
are permitted; changing order, seed or policy is not.

An omitted or null cursor denotes the first page and sets `cursor_offset` to
zero. A supplied cursor must match exactly
`^ph1:([1-9][0-9]{0,2}):([0-9a-f]{64})$`; leading zeroes, signs, whitespace,
uppercase hashes and extra characters are invalid. Its parsed `next_offset`
must be smaller than `eligible_observation_count` and, because the fixed
candidate limit is 500, is in the range 1 through 499. The binding hash covers
exactly:

```json
{
  "schema_version": "paragraph_history_cursor_binding.v1",
  "filesystem_snapshot_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "seed_binding_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "order_binding_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "projection_policy_sha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd",
  "limits_sha256": "eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee",
  "full_result_set_sha256": "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff",
  "result_order": "seed_then_descending_position_v1",
  "next_offset": 2
}
```

`binding_sha256` is the `canonical_json_v1` SHA-256 of that exact object. The
offset encoded before the hash must equal `next_offset`. Syntax or numeric-range
failure is `invalid_cursor`; a syntactically valid cursor whose offset or digest
does not equal the recomputed binding is `cursor_mismatch`. `max_items` is not
in the binding, so a later page may request a different valid size.

Let `R` be the complete `observations` array committed by
`full_result_set_sha256`, let `N = len(R)`, and let `o` be zero for the first
page or the parsed cursor offset. The page is exactly `R[o:o+n]`, where `n` is
the greatest positive integer for which `o+n <= N`, `n <= max_items`, and all
returned live strings fit the fixed one-million-character page verbatim cap.
`returned_observation_count` equals `n`. If `o+n < N`, `next_cursor` is non-null
and both its textual offset and its binding payload's `next_offset` equal
`o+n`; if `o+n == N`, `next_cursor` is exactly null. Thus consecutive pages
neither overlap nor omit an observation.

Adding the next observation past the page cap creates `next_cursor`; it is not
a resource failure. One observation is never split or text-truncated, and its
200,000-character individual cap is strictly below the page cap, so `n` is at
least one for every valid request. An observation above its own cap refuses the
complete operation.

The existing journal is not semantic input to this first slice. Local apply
records neither create nor resolve paragraph-history relationships. Therefore
the tool's own successful record append, or any other otherwise valid journal
append between pages, does not invalidate the filesystem/result cursor.
Journal contention, corruption or oversize can make the post-result record
publication fail; the valid DOCX result still returns with
`record_status: write_failed`. A journal condition never becomes DOCX evidence.

## Projection-computation scope

The live algorithm has one exact accounting domain:

- accepted/current readings are indexed for every in-scope canonical paragraph
  in every captured candidate;
- the rejected-pending projection and selected-paragraph change-unit view are
  materialized only for the seed and for each paragraph subsequently selected
  by an `exact_unique` step;
- ambiguous, unresolved and blocked lower observations have no selected
  paragraph projection or selected change-unit view; and
- projection status/state counts and rejected-text budgets cover exactly that
  evaluated selected-paragraph set.

The shared extraction implementation may internally classify additional
revision elements to enforce its existing whole-DOCX safety/resource checks,
but those elements are not history observations and do not enter selected
projection counts. The exhaustive adjacent-pair classifier in the acceptance
suite is a separate test helper that intentionally projects every eligible
right-hand paragraph; it is not the live tool's computation or coverage model.

Hidden/deleted text is charged independently; the accepted/current character
budget never makes it free. Each decoded scalar is charged to the applicable
projection once per document snapshot, not once per comparison. Change-unit
old/new text is additionally charged to its explicit budget because it is a
separate returned surface.

`decoded_text_chars_per_folder` is the sum of indexed accepted/current text,
materialized selected rejected-projection text, and selected change-unit
old/new text. Context strings derived as substrings of already charged current
text are not decoded a second time, but every repeated live string is still
charged to the returned-verbatim caps.

Because this slice selects at most one paragraph per DOCX observation, its
rejected per-DOCX cap is intentionally coextensive with the per-paragraph cap.
A later multi-paragraph expansion must choose a new meaningful document
aggregate instead of silently inheriting 50,000 characters for the whole file.

`has_non_whitespace` and match eligibility use the fixed
`xsd_whitespace_v1` set U+0009, U+000A, U+000D and U+0020. At least one other
Unicode scalar makes the flag true. This does not depend on the host Python's
Unicode whitespace tables. Text hashes remain SHA-256 of exact UTF-8 bytes;
whitespace is never collapsed for equality.

Both returned-verbatim caps charge the complete live string surface enumerated
in coverage, including paths and metadata, while digest-only hidden candidate
lists contribute no verbatim characters beyond their returned samples.

Exceeding a DOCX/result hard cap refuses the whole operation with
`resource_limit_exceeded`. The journal's established `journal_oversize` code
occurs only during post-result record publication and therefore returns the
valid result with `record_status: write_failed`.
Candidate samples may be truncated only after the complete count and digest
are known. No malformed/oversized candidate or relationship is silently
skipped. Cancellation and elapsed time never select a partial success.

`exact_candidate_relationships` caps the complete positive candidate
relationship population across exact-unique, ambiguous and
positive-but-insufficient unresolved steps, not only the relationships chosen
for propagation.

paragraph_history_all_navigation_candidates.v1, candidates: [...]}`, where the
complete candidate objects are ASCII-sorted by `(observation_id,
navigation_candidate_id)`; it never digests only the returned page or samples.

Positive exact text relationships inside the declared body-flow scope remain
valid even when other parts/containers are excluded. Zero candidates means no
match only in that declared inspected scope. It never establishes whole-DOCX
absence or deletion.

## Paragraph-side `verify_quote` v0.4 contract

`paragraph_ref.v1` remains the only paragraph anchor and continues to bind the
accepted/current text. It is not forked to carry a rejected-projection hash.

Under MCP contract v0.4, `verify_quote` gains one optional named input:

```json
{
  "paragraph_projection": "accepted_current_v1"
}
```

Allowed values are `accepted_current_v1` and
`pending_text_revisions_rejected_v1`. Omission or explicit null preserves the
existing accepted/current behavior. A non-null selector is valid only with a
complete `paragraph_ref.v1`; supplying it with a legacy or v2 change-unit
anchor is `invalid_projection_selector`.

The selected projection and the anchor are rebuilt from one captured byte
snapshot. An unavailable rejected projection fails with
`paragraph_projection_unavailable`; it is not a `not_found` verdict.

The v0.4 operation result contains exactly:

```json
{
  "schema_version": "verification_result.v2",
  "verdict": "exact",
  "exact": true,
  "checked_anchor": {},
  "checked_projection": {},
  "matches": [],
  "diff": []
}
```

The existing common producer/record metadata is added at the MCP boundary.
`checked_anchor` is the complete re-resolved input anchor. The result is one of
three closed variants:

- a legacy/v2 change-unit anchor requires `checked_projection: null` and reuses
  the existing old/new match object unchanged;
- an accepted/current paragraph has the projection object below and only
  `side: paragraph_current`; or
- a rejected-pending paragraph has the projection object below and only
  `side: paragraph_rejected_pending`.

For either paragraph variant, `checked_projection` contains exactly:

```json
{
  "schema_version": "verified_paragraph_projection.v1",
  "mode": "pending_text_revisions_rejected_v1",
  "projection_status": "complete",
  "anchor_reading_mode": "accepted_current_v1",
  "anchor_paragraph_text_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "projection_text_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "text_length": 137
}
```

For current mode the two hashes are equal; for rejected mode they may differ.
The paragraph match object contains exactly the existing `path`, `part_name`,
empty `revision_ids`, nullable `clause`, `paragraph_index`, current-anchor
`paragraph_text_sha256` and `reading_mode: accepted_current_v1`, plus
`projection_mode`, `projection_text_sha256`, and the corresponding closed
`side`. `matches` contains zero objects for `not_found` and exactly one for
`exact` or `normalized`. The existing deterministic verdict/diff rules remain
unchanged.

An unavailable rejected projection fails before a result with
`paragraph_projection_unavailable`; it is never converted to `not_found`.

MCP v0.4 adds the permanent writable pair
`(verify_quote, verification.v2)`. The existing
`(verify_quote, verification.v1)` remains a recognized permanent historical
pair and is never rewritten; new v0.4 calls write v2. A v0.4 reader/exporter
must read both. A v0.3 reader does not know v2 and may refuse a journal after
its first v2 frame; this is the explicit downgrade boundary.

A successful v2 raw record stores `status: ok` plus the exact operation result
above; an attempted failure stores exactly `{status: error, error_code, error}`
under the existing controlled-error rules. Raw input retains the private quote
under the current local policy. Compact input remains the exact
`{sha256, omitted: true}` digest envelope. Compact error result is exactly
`{status: error, error_code, error_sha256, error_omitted: true}`. Compact
success result contains exactly `status`, `schema_version`, `verdict`, `exact`,
the existing path-free `checked_anchor` summary, the closed checked-projection
object, `matches`, and `diff_count`; it contains no quote or paragraph text.
For paragraph matches, `matches` is exactly
`{count, sha256, sample, truncated}`. Its complete sorted entries contain
exactly `side`, `part_name`, `paragraph_index`, `paragraph_text_sha256`,
`reading_mode`, `projection_mode` and `projection_text_sha256`; the sample is
the first at most 20 entries and the digest covers the complete array under
`verification_v2_compact_matches.v1`. Change-unit matches reuse the existing
v1 path-free observed-match summary; they do not add old/new text.

The paragraph-history result is self-contained: a host does not need to call
`verify_quote` for every row. The selector exists for independent follow-up
verification of a quoted current or rejected-pending string.

## Journal and privacy boundary

The future history pair is success-only. A failure before a valid result writes
no `paragraph_history.v1` record or sidecar. After a valid result exists, record
publication failure returns that result with `record_status: write_failed` and
a controlled `record_error`; it never changes machine facts.

The live result may contain bounded selected paragraph text, change-unit
old/new text, filenames, paths, headings and projected OOXML author/date
metadata. This is necessary for an immediately useful local brief and is
controlled by the fixed per-observation and per-page limits.

The private raw record may retain the caller's folder/seed paths and explicit
filename sequence under the existing private-local input policy. Because this
first slice has no assertion or contract-text input, it does not add arbitrary
free text to that retained input. The stored result is a minimized summary:

- hashes, counts, policy/snapshot digests and resolution states;
- path-free seed and selected reference identities;
- bounded item identifiers/hashes and at most the fixed sample; and
- no paragraph text, change-unit text, headings, labels, author/date strings or
  raw errors.

That stored raw-record `result` contains exactly:

```json
{
  "status": "ok",
  "seed": {},
  "ordering_source": "explicit_filename_sequence_v1",
  "result_order": "seed_then_descending_position_v1",
  "filename_manifest_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "snapshot": {},
  "coverage": {},
  "limits": {},
  "next_cursor_sha256": null,
  "observations_summary": {
    "count": 4,
    "sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "sample": [{
      "observation_id": "rm_obs_v1:...",
      "position": 3,
      "entry_role": "seed",
      "resolution_state": null,
      "resolution_reason": null,
      "observation_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc"
    }],
    "truncated": false
  }
}
```

`seed`, `snapshot`, `coverage` and `limits` are the exact path-free closed
objects already defined. `observations_summary` covers the returned page in
live result order. Each `observation_sha256` digests the corresponding complete
live observation; the summary `sha256` digests exactly
`{schema_version: paragraph_history_returned_observations.v1, observations:
[...]}` with that complete page. Its sample is the first at most 20 path-free
summary entries and is truncated exactly when `count` exceeds sample length.
The stored `filename_manifest_sha256` is the declared-order digest from
`order_basis`, not the independent sorted candidate-manifest digest.

`next_cursor_sha256` is null for a null live cursor; otherwise it is the
`canonical_json_v1` SHA-256 of exactly `{next_cursor: <complete live cursor>}`.
The outer record's `tool_result_sha256` still binds the complete normalized live
result before record metadata; its `result_sha256` binds only this stored
summary.

Compact export digests the complete input and omits paths, filenames, text,
navigation strings, author/date metadata and future assertion payloads. It is
not a reconstruction of the live result and does not make the local unsigned
journal tamper-evident.

The compact projection retains the existing `decision_record.v1` envelope. Its
three tool-specific projections are exactly:

```json
{
  "input": {
    "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "omitted": true
  },
  "result": {},
  "provenance": {
    "filesystem_snapshot_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "full_result_set_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
    "projection_policy_sha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd",
    "current_reading_mode": "accepted_current_v1",
    "rejected_reading_mode": "pending_text_revisions_rejected_v1",
    "container_policy": "canonical_body_flow_v1",
    "result_order": "seed_then_descending_position_v1"
  }
}
```

`input.sha256` digests the complete canonical raw input. `result` is exactly
the stored minimized result above, without reintroducing live observations.
The common live record metadata tuple remains closed: `written` requires a
non-null record id and forbids `record_error`; `disabled` requires null id and
forbids the error; `write_failed` requires null id and one bounded controlled
error string.

## Controlled failures

The first-slice tool uses this closed failure table:

| Phase | Condition | Outcome |
| --- | --- | --- |
| Input | malformed named/nested field | `invalid_request` |
| Input | malformed `paragraph_ref.v1` | `invalid_reference` |
| Input | missing/invalid explicit order declaration | `invalid_round_order` |
| Input | seed not last declared position | `seed_not_last_declared_position` |
| Input | malformed/foreign cursor | `invalid_cursor` |
| Workspace | missing/not directory/unreadable/drifting folder | `workspace_missing`, `workspace_not_directory`, `workspace_unreadable`, or `workspace_changed` |
| Candidate | symlink, non-file or hard link | `unsafe_candidate` |
| Candidate | byte/name identity drift | `workspace_changed` |
| Candidate | bytes cannot be opened/read | `file_unreadable` |
| Seed | path is not a direct candidate | `seed_not_candidate` |
| Seed | file hash drift | `file_sha256_mismatch` |
| Seed | valid ref no longer resolves or policy/text differs | `reference_mismatch` |
| Seed | resolved current text is empty or whitespace-only | `seed_not_match_eligible` |
| DOCX | malformed package/XML | `invalid_docx` |
| DOCX | missing main document part | `missing_document_part` |
| DOCX | ambiguous/unsupported structure | `file_unextractable` |
| DOCX | unsupported compression | `unsupported_compression` |
| DOCX | encrypted/masked member | `encrypted_docx` |
| Projection | combined revision nesting above two | `resource_limit_exceeded` with `limit: revision_nesting_depth` |
| Resource | any fixed non-journal cap exceeded | `resource_limit_exceeded` |
| Evidence | equal SHA-256 but unequal fully compared text | `evidence_consistency_error` |
| Cursor | candidate/result/order/policy drift | `cursor_mismatch` |
| Output | result violates the closed contract | `output_contract_error` |
| Common boundary | unexpected non-parser exception before a valid result exists | sanitized `internal_error`, with no history record |
| Journal publication | `journal_busy`, `journal_corrupt`, `journal_oversize`, unsafe sidecar/journal object or I/O failure after a valid result | success with null record id, `record_status: write_failed`, and that controlled code in `record_error` |
| Journal disabled | decision records disabled by configuration | success with null record id and `record_status: disabled` |

An unavailable paragraph projection is normally a successful, explicit
observation. It becomes a controlled tool failure only when the selected
operation specifically requires that projection, as rejected-side
`verify_quote` does.

The closed post-result publication error domain is `journal_busy`,
`journal_corrupt`, `journal_oversize`, `sidecar_symlink`,
`sidecar_not_directory`, `journal_symlink`, `journal_not_file`,
`journal_hardlink`, `gitignore_symlink`, `gitignore_not_file`,
`gitignore_hardlink`, `gitignore_invalid`, `workspace_changed`,
`workspace_not_directory`, `workspace_unreadable`, `record_invalid` or
`internal_error`. Each appears only as the bounded `record_error` of a
successful `write_failed` result.

The deterministic phase order is: validate named/nested input and reference
syntax; validate cursor syntax; open/enumerate the workspace; enforce candidate
count and safe types; validate complete order, seed membership and last seed
position; capture all candidate bytes and recheck the set; parse/index
candidates in ascending declared order; re-resolve the seed; execute the
backward trace and selected projections; assemble and validate the complete
seed-first result set; compare cursor binding; validate the outgoing closed
result; then attempt journal publication. Capture, package/XML parse,
accepted/current indexing and their global resource checks use the first failing
candidate in ascending declared order. Rejected-projection and selected
change-unit failures use the first selected paragraph encountered by the
seed-first descending trace. Seed re-resolution precedes cursor comparison, so
seed drift retains its specific code. No pre-result failure writes a history
record.

All other DOCX parser/library failures normalize to `invalid_docx`; any other
unexpected pre-result exception normalizes to `internal_error`. Exception class
names, paths and document text are not part of either public error. Refusals are
MCP tool errors rather than successful result-union objects.

## Acceptance fixtures for later implementation

All initial fixtures are synthetic and redistributable. The first
implementation is not accepted until at least these cases pass.

1. The shipped four-round liability-cap paragraph traces from the last-position
   seed through all four observations using exactly three adjacent
   `rejected_projection_equality` relationships:
   rejected(R4) = current(R3), rejected(R3) = current(R2), and rejected(R2) =
   current(R1). Every comparison includes hash agreement and full-string
   equality.
2. A separate adjacent-pair classifier validates the projection algorithm. For
   every non-whitespace canonical accepted/current paragraph in the right-hand
   document, it first classifies exact current matches against all left-hand
   current paragraphs (`unique current`, then `ambiguous current`); only with
   zero current matches does it classify one eligible rejected projection as
   `unique rejected`; otherwise it is `unmatched`. The exact counts are:

   | Transition | Unique current | Ambiguous current | Unique rejected | Unmatched |
   | --- | ---: | ---: | ---: | ---: |
   | R1 → R2 | 59 | 2 | 4 | 2 |
   | R2 → R3 | 62 | 2 | 3 | 1 |
   | R3 → R4 | 65 | 2 | 1 | 0 |

   The arrows denote adjacent declared positions only, not verified time.
   These are classifier fixtures, not a claim that source version 0.3.0
   already implements the history tool.
3. Two of the R2 → R3 rejected matches exercise literal `moveTo`/`moveFrom`
   visibility. The result exposes wrapper visibility but no move pairing,
   move event, chronology or lineage.
4. Stray `w:delText` outside a valid deletion/move-from context makes the
   affected projection unavailable and never injects that text.
5. Paragraph-mark insertion/deletion and row/cell/table existence revisions
   make affected projections unavailable; formatting-only property history is
   counted without corrupting otherwise complete literal text.
6. Mixed nested text/move wrappers at depth two follow the insertion-like-
   ancestor priority. Depth three refuses the whole call without approximation.
7. A file whose revisions were accepted/flattened cannot expose the overwritten
   wording: its rejected projection equals its current text. If that
   current text changed, the thread therefore breaks honestly instead of
   triggering fuzzy recovery.
8. A complete empty or whitespace-only rejected projection creates no
   equality edge and no `new_clause`/insertion claim. An empty projection is
   still returned as a positive projection observation.
9. A rejected projection exactly equal to its own current text sets
   `equals_current: true` and creates no redundant rejected-projection edge.
10. Two exact candidate paragraphs in one lower observation remain
    `ambiguous`; a unique current candidate plus an unavailable rejected
    projection remains `unresolved/rejected_projection_unavailable`; and one
    unique current candidate plus a different unique rejected candidate is
    `ambiguous/multiple_exact_candidates`.
11. Duplicate `Exclusions` headings remain navigation-only and never resolve a
    paragraph or permit propagation.
12. Once one position is ambiguous or unresolved, all still-lower positions
    use the appropriate blocked reason and no gap is skipped.
13. Byte-identical DOCX files under two filenames remain two position
    observations. Renaming changes observation identity, while changing bytes
    makes an old seed stale.
14. Equal hashes are not trusted without a full-string-comparison test seam.
15. Seed/file/set drift between pages yields the specific reference or cursor
    refusal; pagination has no observation overlap or omission.
16. A malformed, encrypted, unsafe or resource-exceeding candidate refuses the
    complete result. Every fixed cap passes exactly at the boundary and refuses
    one over.
17. Current and rejected-projection text hit their independent per-paragraph,
    per-DOCX and folder budgets. Selected change-unit text hits its
    per-observation, complete-result and returned-verbatim budgets.
18. Journal contention/corruption/oversize and post-result publication failure
    retain their distinct semantics. The tool's own record does not invalidate
    its next cursor page.
19. Raw-record and compact-export fixtures prove that live paragraph/change
    text, paths, filenames, headings, labels and author/date strings do not
    leak into the minimized stored result or compact projection.
20. `verify_quote` defaults to current paragraph behavior, verifies the
    rejected side only when explicitly selected, returns that side's own hash,
    and refuses an unavailable projection. Historical `verification.v1`
    records remain readable after v2 writes begin.
21. English product acceptance gives a lawyer who did not run the tool enough
    evidence to identify a candidate file for further whole-document baseline
    review and list open questions. The brief does not establish that the file
    is a suitable baseline for the agreement as a whole.
    The lawyer must not mistake positional order, projection equality, a Word
    author/date string or host prose for chronology, actor identity, approval
    or clause lineage.
22. Russian and other Unicode text is mechanically preserved, but semantic
    discovery, morphology, translation and localized legal interpretation are
    not product-acceptance claims.

External or sanitized real-matter validation may follow, but it does not
replace the deterministic synthetic acceptance suite and must never introduce
confidential matter text into the repository.

## Product claim boundaries and non-goals

The first Stage 3C slice does not:

- reconstruct the history of every paragraph in a contract;
- trace a multi-paragraph or semantic clause;
- use fuzzy, vector, translated, morphological or similarity matching;
- infer that wording was introduced, deleted, restored, countered, conceded,
  accepted or reinstated;
- establish chronology from filename, manifest position, mtime or OOXML date;
- establish actor, sender, approver, authorship, custody or intent from OOXML
  metadata or a local file;
- pair move ranges or claim a move event;
- invert paragraph, row, cell, table or other structural revisions;
- recover history removed by accepting/flattening revisions;
- consume the local journal as paragraph-lineage evidence;
- accept caller assertions in the first slice;
- make whole-DOCX negative claims;
- create a DOCX, PDF or separate history-report file;
- select a legally correct baseline; or
- provide legal advice, a trusted timestamp, authentication, digital signature
  or tamper evidence.

## Stage 3D remains a separate write product

Stage 3C explains what the available snapshots mechanically preserve about one
paragraph thread. It never changes those snapshots.

Stage 3D, if separately validated and specified, would solve a different job: a
clean sendable redline from one explicit baseline. That future write workflow
requires complete accept/reject/normalize dispositions, a new output artifact,
an independent preflight proof and fail-closed publication. It must never
silently flatten, overwrite or reinterpret the negotiation evidence that Stage
3C reads.

Completing Stage 3C does not automatically approve Stage 3D. External-user
validation remains the gate between the two stages.

## Definition of done for the later core

Stage 3C core is ready for an exact-build product gate only when the future
implementation matches every closed schema, algorithm, claim and failure
boundary above; all acceptance fixtures and complete local quality gates pass;
an installed artifact advertises the intended v0.4 tool and verification
surfaces; compact privacy is independently checked; and the exact artifact
passes a separate English Claude Desktop acceptance.

None of those gates is satisfied merely by merging this specification.
