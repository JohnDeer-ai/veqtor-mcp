# Приёмка большого обновления Veqtor на копиях договоров

Статус: план проверки, результаты ещё не получены.

Этот план проверяет [спецификацию обновления](NEGOTIATION_ROUND_RELEASE_SPEC_RU.md). Для каждого сценария фиксируются источник, действие, заранее ожидаемый результат и фактический результат установленного кандидата. Тесты XML, успешный вызов инструмента и отсутствие ошибок Word — отдельные свидетельства; ни одно не заменяет остальные.

Документ ведётся отдельно от PR 100 и не заявляет реализацию новых функций. Реальная пара «отправлено/получено» пока не выбрана пользователем; реальный корпус не заморожен. Все числа, цитаты, метки и условные обозначения в публичных примерах ниже вымышлены и не взяты из конкретной сделки.

## Корпус до разработки

| Набор | Состав | Назначение |
| --- | --- | --- |
| T | Вымышленные синтетические документы с заранее описанными структурой и результатами | Начальная разработка, все поддерживаемые формы и отказы, воспроизводимые регрессии без реальной истории |
| A | Выбранная пользователем пара отправленного/полученного реального двуязычного договора с основным текстом в таблицах | Сравнение, правки двух колонок, свойства, числа, комментарии, вставка/удаление строки, нумерация, исходящий комплект |
| B | Выбранная пользователем пара отправленного/полученного другой реальной сделки с обычными и нумерованными абзацами | Решения по тексту/свойствам, удаление пункта, ссылки, сохранение оформления и нумерации |
| C | Сложный реальный образец или независимо подготовленный вариант A/B | Повторяющиеся пункты, объединения ячеек, вложенные исправления, поля, закладки и ожидаемые отказы |

Набор T и пустые шаблоны частных карточек можно готовить и фиксировать сейчас. Реальные A/B замораживаются только после прямого выбора пользователем конкретных файлов и их ролей, затем проверки точных копий и независимых ожиданий. Полученный файл не становится отправленным по названию, датам или разметке. Один выбранный входящий документ может служить техническим образцом, но не заменяет отсутствующую отправленную версию.

Для A и B нужны минимум по одному поддерживаемому сквозному сценарию. C не должен целиком совпадать с материалом, на котором разработчик отлаживал функцию. Независимый проверяющий добавляет контрольные варианты после основной реализации, сохраняя их ожидаемые результаты до запуска кандидата.

Для каждого реального источника составляется частная карточка в отдельной папке корпуса вне репозитория и вне рабочих папок сделок:

- условное обозначение сделки, путь к копии и SHA-256; роль каждого файла и основание выбора отправленной версии;
- число и типы абзацев, таблиц, строк, ячеек и объединений; колонки языков;
- виды существующих исправлений, включая `rPrChange`, `pPrChange`, `tcPrChange`, `trPrChange`, `tblPrChange`, `tblGridChange`, комментарии, связи веток и авторы;
- стили и уровни списков каждой языковой колонки, правила продолжения/перезапуска, ненумерованные разделители;
- списки, разделы, поля, закладки, вложенные таблицы, колонтитулы, сноски, рамки и вложенные объекты;
- заранее выбранные цели успешных операций и цели обязательного отказа;
- версия Word, ОС и формат сохранения.

Цифры структуры вычисляются по выбранным файлам заново и сохраняются только в частной карточке. Публичная спецификация не содержит названий, имён, путей, хешей, цитат или агрегатов конкретных договоров.

Неизменяемые источники приёмки, тестовые рабочие копии, контрольные ожидания и результаты хранятся раздельно в этой частной папке корпуса. Исходные деловые файлы не перезаписываются. Каждый повтор сценария начинается с новой копии; предыдущие неудачные результаты сохраняются. Эта изоляция материалов приёмки не меняет штатное расположение рабочего журнала и позиций Veqtor в папке сделки пользователя.

При отсутствии настоящей пары можно создать контролируемую пару в T либо отдельно обозначенную искусственную производную разрешённого технического образца. Это помогает проверять движок, но не замораживает A/B и не закрывает приёмку сравнения реальной пары. Для подготовленных изменений используются вымышленные тестовые личности, без переписывания реального авторства.

Все преобразования до приёмки перечисляются отдельно. Нельзя заранее принять неподдерживаемые правки, удалить комментарии или упростить таблицу и затем выдать результат за проверку исходного договора. После выбора пользователем A/B блокировка обязательного сценария требует расширения поддержки; заменить договор на удобный ради зелёной проверки нельзя. Отдельное явное изменение пользователем бизнес-объёма фиксируется с сохранением прежнего незакрытого результата. Обезличенная или упрощённая производная имеет отдельный статус и не заменяет проверку исходной структуры.

| ID | Сценарий выбора корпуса | Критерий |
| --- | --- | --- |
| C01 | Подготовить T и шаблоны при отсутствии реальной пары | Общая разработка продолжается; A/B остаются невыбранными, реальные сравнения не объявляются выполненными |
| C02 | Передать только входящий файл либо два файла без ролей | Нет автоматического назначения отправленной версии и заморозки реальной пары |
| C03 | Явно выбрать реальные файлы и роли, затем изменить файл по прежнему пути | В частной карточке сохранены выбранные байты/хеши; новая версия не подменяет снимок |
| C04 | Обязательная операция выбранного A/B блокируется | Требование остаётся открытым до доработки; файл не упрощается и не заменяется ради успеха |
| C05 | Проверить публичные документы, PR и состав папок | Сведения конкретных договоров только в частном корпусе вне репозитория и рабочих папок сделок; T явно синтетический |

## Независимые ожидания

До первого запуска фиксируются точные старые и новые формулировки, разрешённые действия, ожидаемые комментарии, числовые значения с единицами, неизменяемые области и оба исхода структурных правок. Ожидания не извлекаются из результата Veqtor и не меняются, чтобы засчитать его.

Независимые контролируемые варианты включают изменение числа без разметки, обычную правку с разметкой, принятие прежней вставки, перепаковку Word без изменения текста и неподдерживаемую структуру. Сохранённый контроль в Word помогает проверить фактическое поведение, но его автоматическое сравнение не является единственным эталоном.

Для каждого сценария заранее выбирается ожидаемый исход: успех, отказ либо ограниченный отчёт с конкретной неопределённостью. Неожиданный отказ в обязательном успешном сценарии считается незакрытым требованием. Ожидаемый отказ не позволяет заявить поддержку данной структуры.

| D17 | Сохранить выбранную правку свойств в Word, затем перечитать и решить через Veqtor | Обязательная поддерживаемая форма распознаётся по новому снимку; старые ссылки отказаны |

Резервная копия каждой успешной записи в тот же путь должна побайтово совпадать с состоянием перед этой записью. Неудачная предварительная проверка не создаёт изменённый документ, ложную успешную запись или готовый исходящий пакет.

Для D15 каждая поддерживаемая форма проходит принятие и отклонение через Veqtor и независимо в Word на отдельных копиях, включая сохранение и повторное открытие. T покрывает все перечисленные категории; выбранные реальные A/B проверяются без предварительной очистки их существующих правок. D18 допускается только как граница частной сборки и не заменяет D09/D10/D19 итогового выпуска.

| S20 | Одна языковая колонка либо разделитель не проходит предварительную проверку | Обе колонки и разделитель неизменны; частичный набор не опубликован |

Для каждой формы S01, S02, S09 и S15–S18 обязательны четыре отдельные копии: принятие через Veqtor, отклонение через Veqtor, принятие в Word, отклонение в Word. В каждой сохраняются соседние невыбранные чужие правки. Проверяется открытие, сохранение, закрытие и повторное открытие результата. Для контрольных форм дополнительно выполняется сохранение исходной разметки в Word до решения через Veqtor: после свежего чтения объект должен оставаться распознаваемым.

Сравнивается точное ожидаемое видимое содержание и структура, а не байты DOCX после пересохранения Word. Неизменность оригинала и резервной копии, напротив, проверяется по байтам.

Для исходного документа с уже существующими собственными вставками заранее различаются: состояние до новой операции, принятый исходный текст и состояние после отклонения всех правок. Это разные эталоны; резервная копия хранит состояние до операции.

## Два сквозных раунда

Первый раунд проводится отдельно для A и B. В каждой сделке используются подходящие ей операции; абзац из B не подменяет проверку таблицы A.

Сквозная реальная приёмка начинается только после выбора и заморозки пары пользователем. До этого тот же порядок можно отрабатывать на T, явно как синтетический прогон. Подготовленная искусственно следующая входящая версия остаётся контролируемым тестовым раундом, а не утверждением о реально полученной переписке.

1. Установить точный кандидат и начать новую сессию клиента. Передать пути и задачу, не готовую последовательность вызовов.
2. Прочитать позиции и сравнить предыдущую отправленную с входящей версией. Обнаружить заранее заложенные различия и ограничения.
3. Показать конкретный план. Контрольный ответ пользователя заранее задаёт разрешённые формулировки и решения; пропущенный обязательный вопрос нельзя молча исключить.
4. Принять одну простую правку, отклонить другую, решить поддерживаемые изменения свойств, внести свою пословную правку и ответить на комментарий. В A дополнительно изменить обе колонки, вставить нумеруемую строку с выбранным разделителем и удалить другую поддерживаемую строку; в B удалить нумерованный абзац. Цели и ожидаемые результаты фиксируются заранее; пересекающиеся действия выполняются после свежего чтения отдельными пакетами.
5. Проверить журнал, полные затронутые фрагменты, чужие исправления, комментарии и резервные копии. Открыть результат в Word, проверить все страницы с видимой разметкой, сохранить и повторно открыть.
6. Подготовить согласованные исходящие копии и таблицу разногласий. Отдельно проверить чистовой текст, разметку, нумерацию обеих колонок, состав папки, выбранные по правилу ветки и свойства. Явно проверить отключённое правило метки и ветку с чужим ответом.
7. Зафиксировать выбранный исходящий снимок как контрольный отправленный по явному тестовому подтверждению. Это симуляция отправки; письма и реальные контрагенты не используются.
8. Независимо подготовить следующую входящую копию с заранее заданными изменениями. Начать новую сессию без старого диалога, используя прежние позиции и зафиксированный снимок. Повторить сравнение и один полный цикл решения и сохранения.

Сценарий не закрыт, если обязательная операция потребовала ручного исправления результата, редактирования XML, смены автора ради обхода отказа или скрытого исключения вопроса. При обнаружении неподдерживаемой конструкции сохраняется отказ и пересматривается объём до следующего запуска, без переписывания старого результата как успешного.

Частные сборки используются на отдельных копиях разрешённых документов. Они дают возможность проверить готовую часть работы, но не заменяют итоговые D09/D10/D19, реальную приёмку A/B, чистовой экспорт и релизные проверки. До выбора реальной пары возможно закрыть только соответствующую техническую часть. Общедоступная публикация большого обновления одна, после общей приёмки.

## Проверка Word и второго компьютера

Приёмка Word охватывает текст, разметку, таблицы, стили, нумерацию, ссылки, комментарии и границы страниц. Для финальных сквозных файлов просматриваются все страницы с видимыми исправлениями; для чистового проекта — все страницы его отдельного представления. Отмечаются версия Word, ОС, выбранное отображение, путь и хеш сохранённого файла.

На втором компьютере устанавливается тот же кандидат. Пользователь проверяет своё точное имя и инициалы в Word. На отдельной копии он продолжает уже созданную собственную вставку и создаёт новую правку/ответ, сохраняет, закрывает и снова открывает файл. Фиксируются фактические подписи и характер разметки. Неуспех не маскируется изменением старых авторов.

Дополнительный профиль проверяется только если пользователь его настроил. Вымышленный неразрешённый профиль проверяется без сохранения. Если второго компьютера нет, соответствующий критерий остаётся открытым, а переносимость не объявляется подтверждённой.

## Установка и восстановление предыдущей версии

На отдельной тестовой установке выполняется цепочка «предшествующая публичная версия → кандидат → предшествующая версия → тот же кандидат», затем удаление расширения. В каждом состоянии проверяются реально запущенный пакет, настройки автора, доступные инструменты и сохранность рабочих файлов.

Старый клиент проверяется на отдельной совместимой рабочей папке. Новые снимки и журналы сохраняются, но их обратная совместимость не предполагается: неподдерживаемая версия должна обнаруживаться без изменения данных. После возврата кандидата его записи снова читаются; незавершённые операции восстанавливаются без повторного изменения DOCX. Удаление расширения не удаляет договоры, позиции или журнал без отдельного явного выбора.

## Доказательства и решение о готовности

Для каждого сценария сохраняется краткая карточка результата:

| Поле | Обязательное содержание |
| --- | --- |
| Идентичность | Коммит и дерево исходников, версии/хеши установленного пакета и протокола, клиент, Word, ОС |
| Вход | ID сценария, хеши снимков, независимые ожидания, выбранный автор |
| Действие | План, конкретное решение пользователя, предпросмотр и результат фактического применения |
| Выход | Файлы и хеши, резервные копии, записи журнала, полное перечитывание затронутых объектов |
| Word | Сохранение и повторное открытие, проверенные страницы/исходы, снимки экрана с привязкой к файлам |
| Оценка | Успех, ожидаемый отказ, ограниченный результат, ошибка или не выполнено; незакрытые расхождения |

Результат допускает независимое повторение без доступа к прежнему диалогу агента. Все карточки и доказательства конкретных договоров остаются в частной папке корпуса вне репозитория и рабочих папок сделок. В PR публикуются только общий обезличенный итог без названий, имён, путей, договорных хешей, цитат и агрегатов, а также вымышленные синтетические минимальные регрессии. Хеши программных артефактов и исходного кода допустимы отдельно от сведений договоров.

Перед выпуском независимый проверяющий закрывает каждое обязательное условие, включая отсутствие ложноположительных утверждений о чистоте, равенстве языков и полноте сравнения. Ни одна обнаруженная ошибка сохранности текста, авторства, чужих комментариев или исходных файлов не остаётся принятой как «известное ограничение».

Полный набор автоматических проверок проходит единым чистым запуском на итоговом кандидате. Нативные доказательства соответствуют его установленным байтам. Если после приёмки меняется код, который мог повлиять на результат, затронутые сценарии повторяются; перенос старого доказательства требует явного обоснования неизменности.

Публикация, проверка реально опубликованных артефактов и обновление подключений — последующие отдельные действия. Готовая спецификация и заполненная таблица планируемых проверок сами по себе не означают готовый релиз.
